## 1. Навіщо

Зараз вкладка «Характеристики» показує дані, зібрані з карток sun-ice.com.ua
(`data/specs-*.json`). Власник (2026-10-19): «на сайті все не точно і не так повно».
Джерелом правди стає таблиця **ТЕХНІЧНІ ХАРАКТЕРИСТИКИ** з PDF-каталогу
`Sun-ice — довідники/catalog-mhi-rac-pac.pdf` (152 стор., текстовий шар є на всіх
сторінках, це НЕ скан — OCR не потрібен і застосовувати його не можна).

Каталог дає те, чого на сайті немає взагалі: макс. пусковий струм, заводська заправка
й GWP холодоагенту, діаметри труб, макс. довжина траси й перепад висот, дозаправка
г/м, переріз силового й міжблочного кабелю, номінал автомата, міжлапна відстань опор,
циркуляція повітря по 4 швидкостях, рівень звукової **потужності** окремо від тиску.

## 2. Рішення власника (2026-10-19)

1. **Пілот — одна серія ZSX-W.** Масштабуємо лише після того, як власник підтвердить
   результат. Причина: у разі провалу мало відкочувати.
2. **Варіант компоновки Б:** вміст вкладки «Характеристики» береться з каталогу,
   а не з сайту. Нових екранів не додаємо.
3. **Вкладок стає три** (у адміна чотири): `Тех. дані` · `Функції` · `Аксесуари`
   (· `Наявність`). Підписи скорочені: чотири довгі підписи на екрані 360 px
   обрізаються многоточием, бо вкладки ділять ширину порівну (`flex: 1 1 0`).
4. **У «Тех. даних» одразу видно рівно 10 рядків** у цьому порядку:
   холодопродуктивність · теплопродуктивність · SEER · SCOP · розміри · міжлапна
   відстань опор · макс. довжина труб · макс. перепад висот · заводська заправка ·
   дозаправка холодоагенту.
   Нижче кнопка **«Усі характеристики»** — розкриває ПОВНУ таблицю в порядку каталогу,
   **включно з цими десятьма**. Не «решта», а вся таблиця: людина бачить її так само,
   як у друкованому каталозі.
5. **Комплектацію з коробки НЕ робимо.** Її в каталозі немає, вигадувати не будемо.
   Те, що в каталозі позначено «опція», — це додаткові можливості комплектації,
   і живе воно у вкладці «Аксесуари».
6. **ІІ-пошук — у плани на майбутнє**, у цій роботі не чіпаємо
   (`claude/mhi-catalog/ІІ-ПОШУК-НА-МАЙБУТНЄ.md`).

## 3. Головна технічна проблема: розбір таблиці

**Плоске витягання тексту для цього каталогу непридатне.** Перевірено на стор. 34:
`pdftotext -layout` зсуває підписи й значення на один-два рядки — рядок
«Електроживлення · кВт · 2.0 (0.9 - 3.4)» насправді є холодопродуктивністю, а
«Теплопродуктивність · 0.31 / 0.47» — споживаною потужністю. Прийняти такий результат
означає залити в застосунок неправдиві цифри, яких ніхто не помітить.

**Розбір робиться по координатах** (`pdftotext -bbox-layout`, poppler уже стоїть):

- підписи беремо з лівої колонки, значення — з колонок під маркуваннями моделей;
- рядок таблиці визначається спільним діапазоном Y, а не порядком у текстовому потоці;
- **об'єднана комірка** (одне значення на кілька моделей, напр. `920 x 305 x 220`)
  розпізнається за тим, що блок тексту центрований і ширший за одну колонку, —
  таке значення копіюється всім моделям, які він перекриває;
- одиниця виміру переноситься з окремої вузької колонки як є, без перерахунків;
- виноски (`*1`, `※1`) зберігаються текстом разом із рядком, не відкидаються.

**У кожного значення обов'язкове поле `page`** — номер сторінки PDF, не nullable.
Немає значення в каталозі → `null` у даних і «—» в інтерфейсі. Не інтерполювати, не
брати «у сусідньої моделі так само», не рахувати за формулою, не брати з інтернету й
не з власних знань про MHI.

**Верифікація — обов'язковий крок, не формальність:**
- сторінки 33–35 рендеряться в PNG (`pdftoppm -r 200`) і звіряються очима, рядок за
  рядком, з витягнутим результатом;
- автоперевірки: споживана потужність менша за продуктивність; SEER/SCOP у межах
  3…12; шум у межах 15…70 дБ(А); немає значення, що однакове в усіх п'яти колонках
  там, де в PDF воно різне (ознака «з'їхало»); немає порожніх обов'язкових полів;
- усі розбіжності й сумнівні місця показуються власнику списком. Нічого не
  виправляється мовчки.

## 4. Де лежать дані

Конвенція проекту: довідкові дані — **статичні JSON у `data/`**, збираються скриптами
в `claude/`, версія через `?v=APP_BUILD`. Supabase сюди не йде: дані read-only,
міняються раз на рік, а файл із кеша service worker працює офлайн і не коштує запиту
при кожному відкритті картки.

Новий файл `data/mhi-catalog.json`:

```
{
  "_about": "...", "source": "catalog-mhi-rac-pac.pdf", "built": "2026-10-__",
  "series": {
    "SRK-ZSX-W": {
      "page": 34,
      "title": "Серія SRK-ZSX-W, -WF. Diamond Series",
      "specs": [                       // порядок = порядок каталогу
        { "name": "Холодопродуктивність (Min~Max)", "unit": "кВт", "page": 34,
          "values": { "SRK20ZSX-W": "2.7 (0.8 - 5.5)", "SRK25ZSX-W": "3.2 (0.8 - 6.0)" } }
      ],
      "functions": [                   // матриця зі стор. 33
        { "name": "3D AUTO", "state": "yes|option|no", "note": "", "page": 33 }
      ],
      "accessories": [
        { "kind": "remote|wifi|filter|adapter", "name": "RC-EX3A(D)",
          "state": "option", "note": "Підключається через адаптер SC-BIKN2-E", "page": 34 }
      ]
    }
  },
  "index": { "SRK20ZSX-W": "SRK-ZSX-W", "SRK20ZSX-WB": "SRK-ZSX-W" }
}
```

- `index` веде від **маркування внутрішнього блока з прайсу** (нормалізованого:
  верхній регістр, без пробілів) до серії. Кольорові виконання (-W/-WB/-WT) ділять
  одну колонку каталогу — це в каталозі так і написано, тому це не домислювання.
- Набір характеристик НЕ зашитий у колонки: це список `{name, unit, values}`.
  У Galactic склад буде інший — файл той самий за формою, міняти нічого не доведеться.
- Збирає `claude/mhi-catalog/build_catalog.py`, конфіг серії — окремим записом
  у скрипті. Другого розбірника під інший каталог у цей самий файл не писати:
  окремий модуль із тією самою точкою підключення.

## 5. Що міняється в застосунку

**`js/12-product-sheet.js`** — єдиний файл з логікою:

- `loadMhiCatalog()` поруч із `loadSpecs()`, той самий патерн (кеш, `?v=APP_BUILD`,
  збій мережі НЕ кешується як «даних немає» — пастка 2026-10-19).
- `psTabs()`: вкладки `specs` («Тех. дані»), `funcs` («Функції»), `acc` («Аксесуари»),
  `stock` («Наявність», лише адмінам). Вкладки `funcs`/`acc` показуються ЛИШЕ коли
  для моделі є запис у каталозі — інакше вони порожні й лише заважають.
- `specsHtml()`: якщо модель є в `index` — малюємо 10 ключових рядків + `<details>`
  «Усі характеристики» з повною таблицею в порядку каталогу. Якщо немає — нинішня
  поведінка з `specs-*.json`, слово в слово як зараз.
- Фото картки лишається зверху, як є.

**`index.html`** — тільки CSS для нових блоків; нових `<script>` немає.
**Виконуваного коду в `12-product-sheet.js` не з'являється** — нові обробники, якщо
знадобляться, йдуть у `js/13-start.js` (правило модулів).

Після правки — `python claude/split-index/set-build.py РРРР-ММ-ДД.N`, інакше телефон
візьме суміш старих і нових файлів.

## 6. Самодіагностика

Нова перевірка `id: 'mhicat'` (вимога власника 2026-10-02: будь-яка проблема має сама
дійти до супер-адміна):

- файл `data/mhi-catalog.json` вантажиться й має очікувану версію;
- кожне маркування з `index` існує в прайсі (інакше серію перейменували й дані
  осиротіли);
- скільки позицій прайсу покрито каталогом, скільки лишилось на даних із сайту;
- **звірка каталог ↔ сайт**: якщо для однієї моделі холодопродуктивність у
  `mhi-catalog.json` і в `specs-*.json` різна — це `info`-примітка з обома числами.
  Не помилка (каталог головніший), але власник має бачити, де сайт бреше.

## 8. Коли додасться Galactic

Доведеться: написати окремий розбірник під їхній каталог і додати його вивід у той
самий `data/*.json` за тією самою формою.
НЕ доведеться: міняти формат даних, код панелі, вкладки чи самодіагностику — склад
характеристик задається списком, а не колонками.
