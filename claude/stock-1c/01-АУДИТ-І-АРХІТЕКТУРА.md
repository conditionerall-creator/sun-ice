# Залишки з 1С у Sun-ice — аудит, архітектура, план (2026-10-02)

Статус: **лише аналіз, код не писався.** Схема: `1С → наш backend (Supabase) → БД → PWA`.
PWA до 1С напряму не звертається ніколи.

## Рішення власника (2026-10-02) — діють як вимоги, оновлюють усе нижче

| # | Рішення | Наслідок |
|---|---|---|
| R-1 | 1С стоїть **на сервері** (не в офісі); конфігурація невідома | Сисадмін має її визначити (ТЗ розд. 1). Якщо це хмарний сервіс 1С (1С:Fresh / BAS Cloud), вихідні HTTP-запити можуть бути заборонені — це перше, що з'ясовуємо. |
| R-2 | **Залишки бачать лише `regional_admin` і `super_admin`** | Перевірка ролі — на сервері (в RPC), а не в браузері. Звичайний `user` і гість не отримують жодного рядка. |
| R-3 | **Регіональний адмін бачить склад свого регіону + склад Києва** (Одеса → Одеса+Київ; Дніпро → Дніпро+Київ). Супер-адмін — усі склади. Київ-адмін — лише Київ | Склади прив'язуються до регіонів (`stock_warehouses.region_id`, Київ = центральний). Фільтр — на сервері за `profiles.region_id`. |
| R-4 | Показувати **кількість по кожному складу** | Бейдж + розгортка по складах. |
| R-5 | Показувати **загальну кількість і вільний залишок** | 1С передає **обидва**: `physical` (всього на складі) і `available` (вільний, мінус резерв). Обидва обов'язкові. |
| R-6 | Місце показу — **бейдж** у рядку прайсу | Окремої картки товару не робимо. |
| R-7 | Працюємо **лише з розділами Спліт-системи, Мульти спліт-системи, Напівпромислові** (MHI і GAL) | Рівно **389 моделей** (84+19 / 60+29 / 161+36). Інші плитки — без залишків. Вивантаження з 1С лише по цих групах. |

Позначки: **NEED FROM USER** — потрібно від власника; **NEED FROM 1C ADMIN** — потрібно від
сисадміна/розробника 1С (повний текст — у `02-ТЗ-для-сисадміна-1С-v3.md`).

### Висновки аудиту (важливо для рішень)

1. **Ключ зв'язку — маркування моделі.** Стабільного коду 1С у застосунку немає, і додати його
   «в БД товарів» нікуди — таблиці товарів нема. Тому зв'язок робимо **окремою таблицею
   відповідності** `stock_product_map` (код 1С ↔ ключ моделі застосунку), а не міняємо прайс.
2. **Картки товару в застосунку немає.** Тап по назві у Спліт/Мульти/Напівпромислових відкриває
   картку на sun-ice.com.ua (рішення власника 2026-10-02, не повертати Google-пошук). Отже «блок
   Наявність у картці» буквально реалізувати нікуди → показ наявності **у рядку прайсу**
   (див. B-6).
3. **Напівпромислові — комплекти.** Один рядок прайсу = внутрішній + зовнішній блок = **дві**
   позиції 1С. Наявність комплекту = `min(залишок внутр., залишок зовн.)`. Те саме для GAL
   (`GBZ18MLQ-W+GCZ18MLNQ-W`). У Мульти-спліт (60+29 рядків) блоки окремі, тож 1:1.
4. **Обсяг малий.** Тепер лише 389 моделей Спліт/Мульти/Напівпром (рішення R-7), у 1С це
   приблизно 300–500 позицій × кілька складів. Приклад «12 542 товарів» з ТЗ — не наш випадок.
5. **Регіони в базі:** Київ, Одеса, Харків, Львів, Запоріжжя, Дніпро (`regions.id` 1–6;
   `profiles.region_id` є в кожного адміна). Це готова основа для фільтра складів (R-3).
   Склад Києва — «центральний», видимий усім адмінам.

## B. Що потрібно додати

### B-1. Архітектура (рекомендація)

```
1С (регламентне завдання, кожні 30 хв)
   │  HTTPS POST, повний зріз залишків, JSON, заголовок Authorization: Bearer <токен>
   ▼
Supabase Edge Function  stock-sync        ← секрет STOCK_SYNC_TOKEN (Edge secrets)
   │  валідація → один SQL-виклик у транзакції
   ▼
Postgres: stock_apply_snapshot()  →  stock_levels  (+ stock_sync_log)
   ▼
RPC get_stock()  (тільки authenticated, RLS/SECURITY DEFINER)
   ▼
PWA: бейдж «Наявність» у рядку прайсу
```

**Чому саме так.** Ми не маємо власного сервера, а Edge Function + Postgres у Supabase вже
освоєні. 1С лише **виходить назовні** (outbound HTTPS) — сисадміну не треба відкривати 1С в
інтернет, мапити порти чи ставити сертифікат на 1С.

### B-2. Спосіб передачі: порівняння

| Критерій | A. 1С → POST у наш API | B. Наш сервер тягне з API 1С | C. 1С дає файл, ми забираємо | D. 1С кладе файл на (S)FTP/сховище |
|---|---|---|---|---|
| Безпека | Висока: токен + HTTPS, 1С нічого не відкриває | Середня: 1С має бути в інтернеті (HTTP-сервіс, firewall, IP-whitelist) | Те саме, що B (файл мусить бути доступний ззовні) | Середня: нові облікові дані на сховищі |
| Стабільність | Висока; ретраї на боці 1С | Залежить від доступності 1С у момент опитування | Така сама | Висока (файл лежить, поки не заберемо) |
| Складність нашого боку | Мала (одна функція) | Середня (опитування, таймаути) | Середня | Середня (поллінг сховища) |
| Складність для сисадміна | Середня: HTTP-запит із 1С (`HTTPСоединение`) | Висока: публікація HTTP-сервісу 1С назовні | Висока | Низька-середня (запис файлу) |
| Швидкість | Майже миттєво | Залежить від інтервалу опитування | Те саме | Те саме |
| Залежність від 1С | Мінімальна (1С просто шле) | Максимальна | Висока | Мала |

**Основний — A (1С → POST).** **Резервний — D у варіанті «1С кладе JSON у приватний бакет
Supabase Storage `stock-import`»** (той самий HTTPS, але файлом; нашу функцію запускає `pg_cron`).
Він потрібен, якщо у 1С немає права/зручності робити HTTP-запити з регламентного завдання.
Варіант B розглядаємо лише якщо 1С **вже** опублікована в інтернет (**NEED FROM 1C ADMIN**).
Оскільки 1С стоїть на сервері (R-1), вихідний HTTPS з нього, найімовірніше, дозволений — але це
треба підтвердити (особливо якщо це хмарний сервіс 1С/BAS, де зовнішні виклики можуть бути заборонені).
Ще один страховий шлях без жодної участі 1С: супер-адмін вантажить `.xlsx/.csv` залишків руками
в адмін-картці (той самий конвеєр валідації) — корисний для запуску й на випадок аварії.

### B-3. Режим: full sync (рекомендація)

Full sync: 1С щоразу шле **повний зріз** залишків. Причини: обсяг крихітний (кілька сотень КБ);
самовідновлення (пропущений запит не лишає «дірок»); немає необхідності відстежувати зміни в 1С
(це найдорожча й найкрихкіша частина incremental); простіша перевірка на «обнуління». Incremental
не робимо — лишаємо поле `mode` у контракті на майбутнє.
Семантика full: **позиція, змаплена на наш товар і відсутня у валідному зрізі = 0.** Не змаплена
позиція нічого не показує (не «0», а «немає даних»).

### B-4. Інтервал

Інтервал не зашиваємо в код: його задає **1С** (регламентне завдання), а пороги — таблиця `stock_settings`
(один рядок, міняється без деплою): `fresh_minutes` (за замовч. **45** — до цього «свіжо»; запас над інтервалом 30 хв),
`stale_minutes` (за замовч. **120** — після цього «може бути неактуальним», тобто пропущено ~4 цикли), `low_threshold` (2),
`min_ratio` (0.5, див. B-5). **Рішення власника (2026-10-02): інтервал відправки — 30 хв.** Зміна інтервалу = правка
розкладу в 1С + при потребі `fresh_minutes`/`stale_minutes` одним UPDATE.

### B-5. Захист від помилкового обнулення (у `stock_apply_snapshot`, усе або нічого)

Новий зріз **не застосовується** (старі залишки лишаються, у `stock_sync_log` статус `rejected` +
причина), якщо: список порожній / структура не відповідає контракту; `generated_at` відсутній,
у майбутньому більш ніж на 10 хв або **старіший** за вже застосований; кількість позицій менша
за `min_ratio` (50 %) від попереднього успішного зрізу; кількість змаплених на наш каталог
позицій у зрізі упала нижче 50 % від попереднього; частка некоректних рядків (нечислова
кількість, від'ємна, дублікат ключа) > 5 %. Дублікат ключа `(код, склад)` у зрізі — це помилка
зрізу, а не «візьмемо останній».

### B-6. Схема БД (нове, нічого існуючого не міняємо)

```sql
stock_warehouses (
  code text pk,                       -- код складу в 1С
  name text,
  region_id int references regions,   -- до якого регіону належить склад
  is_central boolean default false,   -- true = склад Києва: його бачать усі адміни
  show_in_app boolean default true, sort_order int )
stock_product_map (
  code_1c text pk,            -- унікальний код номенклатури в 1С (NEED FROM 1C ADMIN)
  article text, name_1c text, barcode text, unit text,
  app_key text,               -- нормалізоване маркування моделі застосунку; null = не змаплено
  map_source text,            -- 'auto' | 'manual'
  updated_at timestamptz )
stock_levels (
  code_1c text references stock_product_map,
  warehouse_code text references stock_warehouses,
  qty_physical numeric,       -- «загальна кількість» на складі (R-5)
  qty_available numeric,      -- «вільний залишок» = мінус резерв (R-5); check: 0 ≤ available ≤ physical
  synced_at timestamptz,
  primary key (code_1c, warehouse_code) )
stock_sync_log (
  id bigserial pk, started_at, finished_at, status text,  -- ok | rejected | error
  http_status int, mode text, generated_at timestamptz,
  received_count int, updated_count int, unmapped_count int,
  error_count int, error_message text, duration_ms int, snapshot_hash text )
stock_settings (id int pk default 1, fresh_minutes, stale_minutes,
                low_threshold, min_ratio)
```
Прайс **не чіпаємо**. Нормалізація ключа — та сама, що в застосунку (верхній регістр, без
пробілів; комплект — `A+B`). Комплект дає `get_stock` розбиттям ключа по `+` і `min()`.

**Доступ (RLS) — за рішеннями R-2/R-3:** усі таблиці `stock_*` закриті напряму; клієнт читає
лише через RPC `get_stock()` (SECURITY DEFINER, `grant execute` лише `authenticated`, `revoke`
для `anon`/`public`). Усередині RPC на сервері:
1. `public.current_role()` не `regional_admin`/`super_admin` (або профіль заблоковано) → **порожня
   відповідь**, жодних рядків;
2. `super_admin` → усі склади з `show_in_app`;
3. `regional_admin` → склади, де `region_id = public.current_region()` **або** `is_central`.
   Київ-адмін бачить лише Київ.
Запис — лише Edge Function під service role. Журнал і мапінг — тільки супер-адмін.
Склади, яких користувач не має права бачити, у відповідь **не потрапляють взагалі** (не ховаються
на фронті).

**API для PWA** (адаптація `GET /api/products/{id}/stock` до Supabase): один виклик
`sb.rpc('get_stock')` повертає **весь дозволений зріз одразу** (до кількох сотень рядків) +
`last_success_at` і `freshness`; фронт кладе в пам'ять і малює бейджі без запиту на кожен тап.
Відповідь на модель:
```json
{ "key": "SRK50HE-S1", "status": "available",
  "physical": 15, "available": 12,
  "warehouses": [ { "code": "ODESA", "name": "Одеса", "physical": 3,  "available": 3  },
                  { "code": "KYIV",  "name": "Київ",  "physical": 12, "available": 9  } ] }
```
`physical`/`available` верхнього рівня — суми по **дозволених** користувачу складах.
**Комплекти (напівпром.):** кількість комплекту рахується **по кожному складу окремо** як
`min(внутр., зовн.)` і лише потім сумується. Внутрішній блок в Одесі + зовнішній у Києві
комплектом **не вважається** — обережна оцінка, щоб не обіцяти те, чого не зібрати з одного складу.
Окремий серверний кеш **не потрібен**; достатньо кешу на пристрої з TTL 5 хв.

**Актуальність** рахуємо від `last_success_at` (а не від `synced_at` рядка): `fresh` (≤30 хв),
`aging` (до 180 хв — підпис «оновлено N хв тому»), `stale` (>180 хв — «дані про залишок можуть
бути неактуальними», **останнє значення лишається**, не 0). Технічних помилок 1С користувач не бачить.

### B-7. Інтерфейс PWA і діагностика

- **Бейдж у рядку прайсу** — лише для `regional_admin`/`super_admin` і лише в плитках Спліт,
  Мульти спліт, Напівпромислові (MHI і GAL). Колір за **вільним** залишком: `🟢` > порогу,
  `🟡` 1…`low_threshold`, `🔴` 0. Текст: `12 вільно · 15 всього`; якщо все під резервом —
  `🔴 0 вільно · 15 всього`. Нема даних — бейджа немає. **Тап по бейджу** (окремий елемент,
  тап по назві лишається за сайтом) відкриває малий лист «по складах»:
  ```
  Одеса    всього 3   вільно 3
  Київ     всього 12  вільно 9
  Оновлено 4 хв тому
  ```
  Для заблокованого/звичайного користувача й гостя нічого не рендериться й нічого не завантажується.
- **Орієнтація на показ:** у стрічці «Оновлено N хв тому» + стан `stale` (>180 хв) — «дані можуть
  бути неактуальними», останнє значення лишається.
- **Картка адміна «Синхронізація залишків»** у Кабінеті (супер-адмін): остання синхронізація,
  статус 🟢/🟡/🔴, отримано/оновлено/не змаплено/помилок, останні 20 запусків, кнопка завантаження
  ручного файлу, таблиця «моделі прайсу без відповідності в 1С» і «позиції 1С без моделі».
- **Нова перевірка в `DIAG_CHECKS`** (обов'язково за CLAUDE.md): давність останньої успішної
  синхронізації; наявність `rejected/error` у журналі; частка моделей прайсу з відповідністю в
  1С; позиції 1С без моделі; розбіжність «ціна є, а в 1С позиції нема».
- Підняти `APP_BUILD`, запис у CHANGELOG, оновити HANDOFF — за регламентом проєкту.

### B-8. Безпека

Токен 1С — лише в Edge Function secrets (`STOCK_SYNC_TOKEN`), порівняння constant-time, можна
ротувати; фронт і git секретів не містять. Функція `stock-sync` — **єдина з `verify_jwt=false`**
(1С не вміє Supabase-JWT) — це свідоме відхилення від решти функцій, захист — токен + ліміт
розміру тіла + перевірка контракту. Опціонально — IP-whitelist, якщо у 1С статичний IP.
Права на перегляд — R-2/R-3 (перевірка в RPC на сервері; фронт — лише відображення).

**Обмеження, про яке треба знати:** кількість по складах бачать усі адміни тих регіонів, що
відповідають складам. Склад Києва бачать адміни **всіх** регіонів — це ваше рішення R-3.

## Відкриті питання до власника (NEED FROM USER)

Відповіді R-1…R-7 закрили попередні U-1…U-5. Лишилось:
- **V-1. Склад Києва = «центральний».** Підтвердіть: у Києві один склад (чи кілька?) і чи він
  єдиний «центральний»? Чи є окремі склади у Харкові, Львові, Запоріжжі (регіони є в базі, а склади
  в 1С — невідомо)? Остаточно відповість сисадмін (ТЗ розд. 3), але ви знаєте бізнес.
- **V-2. Кількість комплекту на різних складах** — приймаєте «по складу окремо» (див. B-6)?
- **V-3. Поріг «мало».** Що вважати малим залишком (мій дефолт — ≤ 2 шт. вільних)?
- **V-4. Заблокований адмін** (`status` blocked) залишки не бачить — підтверджуєте?
