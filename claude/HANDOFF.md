> нижче). Він МІГ відстати від реального коду, якщо користувач вносив зміни без участі

> статус фічі) — звір grep'ом по `index.html`, а не вір цьому файлу наосліп.

## Що це і навіщо

PWA-застосунок (Progressive Web App) для дилерів/клієнтів компанії Sun-ice, що продає
кондиціонери (Mitsubishi Heavy Industries, Galactic та інші бренди). Замінює паперовий/
Excel-прайс і ручне спілкування: дилер відкриває застосунок на телефоні, дивиться
актуальні ціни, рахує свою націнку прямо в застосунку, стежить за акціями, а
адміністрація модерує заявки на реєстрацію і керує акціями. Інтерфейс — повністю
українською.

## Технології та архітектура

- **Frontend**: один файл `index.html` (vanilla JS, без збірки/фреймворків) + окремий
  `sw.js` (service worker: push-сповіщення, офлайн-кешування, бейдж на іконці) +
  `manifest.json`. Хоститься статично через **GitHub Pages**.
- **Backend**: **Supabase** (Postgres + Auth + Storage + Edge Functions). Немає власного
  сервера — вся логіка або в браузері клієнта, або в Postgres/Edge Functions Supabase.
- Прайс — окремий Excel-файл (`price.xlsx`) у Supabase Storage, парситься на льоту в
  браузері бібліотекою SheetJS (xlsx.js). Оновлення прайсу не потребує деплою коду —
  просто замінити файл у Storage і підняти `version` у таблиці `price_meta`.

## Робочий процес (workflow) — важливо для Claude

- **Немає автоматичного деплою.** Claude редагує `index.html` / `sw.js` / `manifest.json`
  локально в клонованому репозиторії. Користувач вручну заливає змінені файли на GitHub
  через веб-інтерфейс (кнопка "Add file → Upload files"), і вручну виконує SQL у
  Supabase SQL Editor / деплоїть Edge Functions через Supabase Dashboard.
- Комітна історія цього репо складається з коммітів "Add files via upload" — це підтверджує
  ручний спосіб заливання, не git push.
- **У цьому репозиторії НЕМАЄ SQL-скриптів і коду Edge Functions.** Вони існують лише в
  Supabase-проєкті користувача. Раніше (до появи цього файлу) технічна документація і
  SQL велись окремо в Claude Project "PWA Sun-ice" (документи `claude/HANDOFF.md` і
  `claude/project-summary.md` **в тому Project**, не в цьому git-репо). Якщо новий чат
  НЕ прив'язаний до того Claude Project — цієї інформації в нього не буде, і потрібно
  або попросити користувача вставити SQL-файли в чат, або звірити стан напряму в
  Supabase Dashboard.
- **Наприкінці кожної сесії, де змінено файли застосунку**, Claude повинен: (1) оновити
  `claude/CHANGELOG.md` новим записом, (2) за потреби оновити цей файл, якщо змінився
  архітектурний стан/статус фіч, (3) явно продиктувати користувачу покроково, які файли
  залити на GitHub і куди (див. шаблон у кінці CHANGELOG.md).

## Структура застосунку (нижнє меню, 6 вкладок)

1. **🏠 Каталог** — плитки категорій обладнання (`CATALOG_TILES` в index.html). Детальний
   статус наповненості — розділ нижче. У кожному рядку прайсу: назва моделі, ціна,
   кнопка "Поділитися", калькулятор (відняти %/додати %/ввести кінцеву ціну, перемикач
   $/₴), галочка "Підбірка" (кошик). Ціни для незареєстрованих/заблокованих — розмиті
   (UI-заглушка, не справжній захист даних).
2. **🔥 Акції** — картки акцій (БД `promotions`), можуть мати PDF з умовами. Нова акція →
   push усім користувачам + плаваюча кулька "Цікава новина".
3. **👤 Кабінет** — вхід/реєстрація за телефоном+паролем. Доступ (з цінами) відкривається
   одразу зі статусом "На розгляді", адмін підтверджує/блокує заднім числом. Є "Забули
   пароль? Зареєструватися повторно" (Edge Function `reregister-user`). Для
   адміністраторів — адмін-панель.
4. **📞 Контакти** — дані філій з БД (`branches`).
5. **ℹ️ Інфо** — Каталоги (PDF MHI/Galactic), Коди помилок MHI (пошук за миготінням
   індикаторів або текстовим кодом, ~92 записи в БД), "Сумісність блоків MHI" (тільки
   regional_admin/super_admin — таблиці сумісності з дилерських xlsx, закріплена
   шапка+перша колонка, без парсингу/автозіставлення маркувань — див. CHANGELOG
   2026-09-09), "Технічна інфа" — заглушка.
6. **🛠️ CRМонтаж** — вкладка для ролі `installer` (див. CHANGELOG 2026-09-09/2026-09-10),
   видима лише коли `role==='installer' && status==='approved'` (`isApprovedInstaller`,
   рахується в `refreshAccessState()`). Крок 2: персональний список монтажів (CRUD) —
   таблиця `public.installer_tasks` (RLS: кожен монтажник лише свої рядки), форма
   створення/редагування (bottom-sheet), статуси (заплановано/в процесі/виконано/
   скасовано), фільтри (статус/тип обладнання/сьогодні/тиждень/пошук), групування за
   днями. Нагадування/експорт/напарники — ще НЕ реалізовані, окремі майбутні кроки за
   ТЗ користувача.

## Статус плиток каталогу (10 штук) — перевірено кодом 2026-09-08

**Наповнені даними і робочою логікою (5 з 10):**
1. Спліт-системи — mhi+gal (аркуші ПОБУТОВІ / GALACTIC)
2. Мульти спліт-системи — mhi+gal (МУЛЬТИСИСТЕМИ / GALACTIC)
3. Напівпромислові спліт-системи — mhi+gal (НАПІВПРОМ / Galactic LCAC)
4. **VRF (Мультизональні)** — `custom: 'vrf'`, власний парсинг
   (`parseVrfTypeSheet`, `parseGalVrfOutdoorSheet`), окремий рендер `renderVrfList`
5. **Теплові насоси** — `custom: 'heatpumps'`, власний парсинг
   (`parseHeatGuardSheet`, `parseWineGuardSheet`), окремий рендер `renderHeatpumpsList`

**Порожні заглушки "Скоро" (5 з 10):** ККБ (компресорно-конденсаторні блоки), Чиллери,
Вентиляційне обладнання, Повітряні завіси, Конвектори та обігрівачі. Дані для них ще не
узгоджені (незрозуміло, які аркуші прайсу їм відповідають).

> Примітка для історії: старіший саммарі користувача (`sun-ice-project-summary.md`)
> стверджував, що наповнено лише 3 плитки, а VRF і Теплові насоси — теж заглушки. Це
> застаріла інформація — станом на 2026-09-08 обидві вже мають повну реалізацію.

## Ролі й адмінка

- `user` — звичайний дилер/клієнт.
- `installer` — монтажник (роль "CRМонтаж", CHANGELOG 2026-09-09/2026-09-10). Реєстрація
  — той самий механізм, той самий чекбокс "Я монтажник" на формі реєстрації; той самий
  цикл `pending`→`approved`/`blocked`, підтверджує regional_admin/super_admin як завжди.
  Різниця з `user` — доступ до 6-ї вкладки "CRМонтаж" (персональний список монтажів,
  Крок 2 — regional_admin/super_admin туди не заходять і чужих монтажів не бачать).
- `regional_admin` — модерує заявки лише свого регіону (RLS обмежує це завжди, незалежно
  від UI); може редагувати курс долара; в адмінці — спрощений фільтр
  "адміністратори/користувачі/інсталятори", без вибору регіону.
- `super_admin` — бачить і модерує всіх, у будь-якому регіоні; фільтр за чотирма ролями
  (user/installer/regional_admin/super_admin) + фільтр за регіоном; єдиний, хто бачить
  картку "Діагностика прайсу".
- Перший реальний super_admin (Артем) — станом на попередній саммарі ще НЕ зареєстрований
  і не підвищений вручну через SQL. **Перевірити цей факт наново в новому чаті**, він міг
  змінитись.

## Самодіагностика прайсу

При кожному завантаженні прайсу застосунок перевіряє, чи все розпізналось (потрібні
вкладки Excel, різке падіння кількості позицій), і записує проблему в `price_issues` — з
точним "де" (плитка каталогу, бренд). Супер-адмін бачить список у Кабінеті + кнопку
"Перевірити зараз". Проблема "гаситься" сама, щойно хтось завантажить виправлений файл.

## Технічні пастки (важливо не наступити повторно)

- **PostgreSQL-пастка**: `current_role()`/`current_region()` у власних RLS-політиках
  ЗАВЖДИ писати з префіксом схеми — `public.current_role()` — інакше Postgres сприймає це
  як зарезервоване ключове слово і падає з синтаксичною помилкою (траплялось двічі раніше).
- Авторизація — Supabase Auth під капотом працює через email/пароль, тому телефон
  конвертується в синтетичний email (`p<цифри>@sunice.local`).
- Push-сповіщення — Web Push через VAPID-ключі, працює лише для залогінених користувачів
  з профілем (`push_subscriptions.user_id` обов'язковий) — для гостя запитується лише
  системний дозвіл браузера, підписка доприв'язується автоматично після входу.
- Кешування прайсу на пристрої — `localStorage`, звіряється з `price_meta.version`.
- `JOKE_MODE = true` в `index.html` (~рядок 1807) — тимчасові жарт-написи в UI. Прибрати
  виставивши `false`, коли набридне/перед "серйозним" релізом.

## Відоме невирішене питання

Google Play Protect блокує встановлення на Samsung ("Небезпечний додаток заблоковано").
Найімовірніше — задокументований баг у мінтері WebAPK браузера Samsung Internet
(проставляє застарілу службову версію Android). Рекомендація: встановлювати через Google
Chrome, а не Samsung Internet. Це НЕ проблема коду застосунку.
