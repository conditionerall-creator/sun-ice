# data/mhi-compat.json — довідник сумісності блоків MHI

**Похідні дані.** Оригінальний xlsx-файл (внутрішній дилерський документ MHI, не
публічна документація) у цьому репозиторії НЕ зберігається — тільки цей файл,
отриманий одноразовим офлайн-розбором (ETL) єдиної таблиці:

| Файл-джерело | Дата версії |
|---|---|
| `Compatibility of RAC_20260409_Customers.xlsx` (листи RAC + RAC MULTI) | 2026-04-09 |

Архівна версія 2019 року в довідник НЕ входить (за прямою вказівкою: працюємо
лише з актуальною таблицею 2026 року) — попередня версія цього файлу мала
fallback на 2019-й, цю логіку прибрано повністю.

Розбір зроблено вручну в браузері (SheetJS), скрипт — `claude/mhi-compat-etl.js`
у цьому ж репозиторії (можна прогнати заново, якщо MHI видасть нову версію файлу:
покласти xlsx поруч, відкрити скрипт у консолі браузера з підключеною бібліотекою
XLSX, викликати `buildAllV2()`, зберегти результат сюди тим самим форматом).
Повна специфікація граматики маркувань і алгоритму зіставлення — в
`claude/` ТЗ "Розшифровка совместимости блоков RAC (MHI)" (якщо збережено в
репозиторії) або в коментарях самого `mhi-compat-etl.js`.

## Структура файлу

```jsonc
{
  "meta": { "generated_at": "...", "source_file": "Compatibility of RAC_20260409_Customers.xlsx" },
  "rac_rules": [
    { "i": "SRK…ZMX-S", "o": "SRC...ZMX-S", "s": "recommended", "sr": "◎",
      "f": null /* або масив текстів виносок */,
      "d": true /* лише якщо є — означає ☆, модель знімається з виробництва */ }
  ],
  "rac_facts": [
    { "t": "Plural use (twin, triple, double-twin)", "i": "SKM-ZSP-S", "v": "Yes (71)" }
  ],
  "multi_rules": [ /* та сама форма, що й rac_rules, для листа RAC MULTI */ ]
}
```

`i`/`o` — сирий текст маркування зі стовпця/рядка таблиці (може містити wildcard
"…"/бере-без-числа, діапазон, список типорозмірів через кому, кілька варіантів
суфікса через кому, анотацію "(R32)") — розбирається в рантаймі функцією
`parseMhiMarking()` в `index.html` (розділ "Сумісність блоків MHI"), тим самим
алгоритмом, що й ETL (`parseMarking()` в `mhi-compat-etl.js`). `s` — сенс статусу
(`recommended`/`conditional`/`incompatible`), `sr` — сирий символ/текст із
таблиці. `f` — текст(и) виносок: у клітинці за дужками `(*N)`, з рядка над
шапкою, з пронумерованого списку внизу листа, або з рідного коментаря Excel-
клітинки (усі джерела об'єднуються). Порожня клітинка і явний `-` трактуються
однаково як `incompatible`.

## Зіставлення (matcher) у рантаймі

Ввід користувача розбирається `parseMhiMarking()`, з толерантністю до одруку в
префіксі (Левенштейн ≤2 симв. проти відомих префіксів — `SMK71ZR-W` розпізнається
як ймовірний `SRK71ZR-W` з явним попередженням в UI). Пошук — `checkMhiCompatibility()`:
- маршрутизація на лист RAC чи RAC MULTI визначається за префіксом зовнішнього
  блока (`SCM` → RAC MULTI, інакше RAC);
- для листа RAC типорозміри внутрішнього і зовнішнього блоків мають збігатись
  (окрема помилка "розмір не збігається", якщо ні) — для RAC MULTI розмір
  наміряно ігнорується (одна зовнішня одиниця живить кілька внутрішніх різного
  розміру);
- суфікс зіставляється по найдовшому спільному префіксу з варіантами шаблону —
  зайві символи після нього (напр. `-WFT` при шаблоні `-WF`) не блокують збіг, а
  показуються окремою приміткою в UI ("розпізнано базове маркування… а введені
  символи… — додаткові");
- refrigerant (S/W-родина) виводиться із суфікса чи з анотації "(R32)", якщо
  суфікса взагалі нема в шаблоні — сама перевірка родини фреону пропускається.

## Використання в застосунку

Файл підвантажується (`fetch`) лише коли користувач відкриває Інфо → "Сумісність
блоків MHI" — на розмір/швидкість завантаження застосунку при старті не впливає.

## Відомі обмеження (на майбутнє)

- VRF/PAC серії (FDC, KX...) — поза межами цього довідника (тільки RAC/RAC
  MULTI), застосунок явно про це попереджає, а не мовчить "немає даних".
- Значення `◎` проти `〇` у файлі офіційно не розшифровані в самій таблиці (є
  лише відсилання "Please refer to our official technical manual") —
  трактування тут (`◎`=recommended, `〇`=conditional) — робоча гіпотеза за
  конвенцією і за тим, що виноска "no official document" стоїть саме біля `〇`.
- У листі RAC MULTI одна виноска, прив'язана до об'єднаної (merged) клітинки
  шапки з кількома типорозмірами, застосовується до всіх типорозмірів у межах
  об'єднання, навіть якщо текст виноски стосується лише одного з них (напр.
  "15 class is WiFi mode" — текст сам це уточнює, тож визнано прийнятним
  спрощенням, а не переробляти на прив'язку до окремої колонки).
