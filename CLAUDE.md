## Що це і навіщо

PWA-застосунок (Progressive Web App) для дилерів/клієнтів компанії Sun-ice, що продає
кондиціонери (Mitsubishi Heavy Industries, Galactic та інші бренди). Замінює паперовий/
Excel-прайс і ручне спілкування: дилер відкриває застосунок на телефоні, дивиться
актуальні ціни, рахує свою націнку прямо в застосунку, стежить за акціями, а
адміністрація модерує заявки на реєстрацію і керує акціями. Інтерфейс — повністю
українською.

## Технології та архітектура

- **Frontend**: один файл `index.html` (vanilla JS, без збірки/фреймворків) + окремий
  `sw.js` (service worker: push-сповіщення, офлайн-кешування, бейдж на іконці) +
  `manifest.json`. Хоститься статично через **GitHub Pages**.
- **Backend**: **Supabase** (Postgres + Auth + Storage + Edge Functions). Немає власного
  сервера — вся логіка або в браузері клієнта, або в Postgres/Edge Functions Supabase.
- Прайс — окремий Excel-файл (`price.xlsx`) у Supabase Storage, парситься на льоту в
  браузері бібліотекою SheetJS (xlsx.js). Оновлення прайсу не потребує деплою коду —
  просто замінити файл у Storage і підняти `version` у таблиці `price_meta`.

## Робочий процес (workflow) — важливо для Claude

- **Немає автоматичного деплою.** Claude редагує `index.html` / `sw.js` / `manifest.json`
  локально в клонованому репозиторії. Користувач вручну заливає змінені файли на GitHub
  через веб-інтерфейс (кнопка "Add file → Upload files" — **треба спершу зайти саме в
  потрібну папку** типу `claude/sql`, інакше файл впаде в корінь репозиторію), і вручну
  виконує SQL у Supabase SQL Editor / деплоїть Edge Functions через Supabase Dashboard.
- Комітна історія цього репо складається з коммітів "Add files via upload" — це підтверджує
  ручний спосіб заливання, не git push. **Claude ніколи сам не робить git push у цей
  репозиторій** — лише готує файли й диктує користувачу, куди їх залити.
- **У цьому репозиторії НЕМАЄ SQL-скриптів (крім `claude/sql/`, які туди явно кладе
  Claude для користувача) і коду Edge Functions.** Стан самих Edge Functions і фактично
  виконаних SQL-міграцій існує лише в Supabase-проєкті користувача — якщо не впевнений,
  що саме вже виконано, попроси користувача звірити напряму в Supabase Dashboard, а не
  покладайся на те, що всі файли з `claude/sql/` вже застосовані.
- **Документація — три файли, різні ролі, не змішувати:**
  - `CLAUDE.md` (цей файл) — статика: стек, конвенції, домен. Міняти лише коли
    архітектура/конвенції реально змінились, не при кожній фічі.
  - `claude/CHANGELOG.md` — хронологія: новий датований запис зверху при кожній
    зміні застосунку (що зроблено, чому, як протестовано, що заливати користувачу).
  - `claude/HANDOFF.md` — поточний стан: що вже готово, що в роботі, відомі
    відкриті питання. Оновлюється перед закриттям кожної сесії, де змінився статус.
- **Наприкінці кожної сесії, де змінено файли застосунку**, Claude повинен: (1) додати
  запис у `claude/CHANGELOG.md`, (2) оновити `claude/HANDOFF.md`, якщо змінився статус
  фіч чи відкриті питання, (3) явно продиктувати користувачу покроково, які файли
  залити на GitHub і куди.
- На старті нової сесії — прочитати цей файл (робиться автоматично) і
  `claude/HANDOFF.md` (там — поточний статус і посилання на CHANGELOG для деталей). Не
  покладатись сліпо на жоден з цих файлів для точних деталей коду — звіряти ключові
  твердження grep'ом по `index.html`/`sw.js`.

## Структура застосунку (нижнє меню, 6 вкладок)

1. **🏠 Каталог** — плитки категорій обладнання (`CATALOG_TILES` в index.html). У
   кожному рядку прайсу: назва моделі, ціна, кнопка "Поділитися", калькулятор
   (відняти %/додати %/ввести кінцеву ціну, перемикач $/₴), галочка "Підбірка"
   (кошик). Ціни для незареєстрованих/заблокованих — розмиті (UI-заглушка, не
   справжній захист даних). Статус наповненості конкретних плиток — динамічний,
   див. `claude/HANDOFF.md`. Плитки з фото (`.menu-tile-photo`) за замовчуванням
   отримують сіру студійну підложку на всю плитку через CSS-градієнт +
   `mix-blend-mode: multiply` на `<img>` (працює для товарних фото з білим тлом —
   білий стає "прозорим", показує підложку). Якщо нове зображення НЕ товарне фото на
   білому/сірому тлі (логотип, кольорова обкладинка, декоративна іконка з власною
   прозорістю) — додати клас `.menu-tile-photo-plain`, інакше підложка/multiply
   спотворять колір.
2. **🔥 Акції** — картки акцій (БД `promotions`), можуть мати PDF з умовами. Нова акція →
   push усім користувачам + плаваюча кулька "Цікава новина".
3. **👤 Кабінет** — вхід/реєстрація за телефоном+паролем. Доступ (з цінами) відкривається
   одразу зі статусом "На розгляді", адмін підтверджує/блокує заднім числом. Є "Забули
   пароль? Зареєструватися повторно" (Edge Function `reregister-user`). Для
   адміністраторів — адмін-панель.
4. **📞 Контакти** — дані філій з БД (`branches`).
5. **ℹ️ Інфо** — Каталоги (PDF MHI/Galactic), Коди помилок MHI (пошук за миготінням
   індикаторів або текстовим кодом), "Сумісність блоків MHI" (тільки
   regional_admin/super_admin — таблиці сумісності з дилерських xlsx, закріплена
   шапка+перша колонка, без парсингу/автозіставлення маркувань), "Технічна інфа" —
   заглушка.
6. **🛠️ CRМонтаж** — особистий список монтажних задач, стаціонарно доступний будь-якому
   залогіненому користувачу незалежно від ролі (регіональне обмеження в назві — данина
   історії, не рольова функція). Раніше був окремою роллю `installer` + фічею
   "напарник" (спільні монтажі між двома інсталяторами) — обидві прибрані 2026-09-10
   як зайве ускладнення для особистого інструменту (див. CHANGELOG). Що лишилось:
   - Список монтажів (CRUD): таблиця `public.installer_tasks`, RLS —
     `installer_id = auth.uid()`, кожен бачить і редагує лише свої рядки. Форма
     створення/редагування (bottom-sheet), статуси (заплановано/в процесі/виконано/
     скасовано), фільтри (статус/тип обладнання/сьогодні/тиждень/пошук), групування
     за днями.
   - Нагадування через `.ics` — іконка 🗓 генерує файл календарної події (VALARM за
     30 хв до початку), чисто клієнтська фіча.
   - Вивантаження списку — тулбар "🖨 Друк" (`window.print()` + CSS `.no-print`/
     `@media print`) і "📊 Excel" (`exportInstallerTasksToExcel()`, SheetJS).
   - Відправка в месенджери — кнопка 🔗 через `navigator.share` (той самий патерн,
     що й "Поділитися" в прайсі/кошику).
   - Не реалізовано: push-нагадування для Android/десктопу (опційна частина ТЗ,
     потребувала б окремого Edge Function + pg_cron за зразком `send-promo-push`).

## Ролі й адмінка

- `user` — звичайний дилер/клієнт. Має доступ і до "CRМонтаж" так само, як усі інші
  ролі — окремої ролі для монтажників немає (прибрано 2026-09-10).
- `regional_admin` — модерує заявки лише свого регіону (RLS обмежує це завжди, незалежно
  від UI); може редагувати курс долара; в адмінці — спрощений фільтр
  "адміністратори/користувачі", без вибору регіону.
- `super_admin` — бачить і модерує всіх, у будь-якому регіоні; фільтр за трьома ролями
  (user/regional_admin/super_admin) + фільтр за регіоном; єдиний, хто бачить картку
  "Діагностика прайсу".

## Самодіагностика прайсу

При кожному завантаженні прайсу застосунок перевіряє, чи все розпізналось (потрібні
вкладки Excel, різке падіння кількості позицій), і записує проблему в `price_issues` — з
точним "де" (плитка каталогу, бренд). Супер-адмін бачить список у Кабінеті + кнопку
"Перевірити зараз". Проблема "гаситься" сама, щойно хтось завантажить виправлений файл.

## Технічні пастки (важливо не наступити повторно)

- **PostgreSQL-пастка**: `current_role()`/`current_region()` у власних RLS-політиках
  ЗАВЖДИ писати з префіксом схеми — `public.current_role()` — інакше Postgres сприймає це
  як зарезервоване ключове слово і падає з синтаксичною помилкою (траплялось двічі раніше).
- Авторизація — Supabase Auth під капотом працює через email/пароль, тому телефон
  конвертується в синтетичний email (`p<цифри>@sunice.local`, `phoneToEmail()` в
  index.html). Будь-який пошук іншого користувача за телефоном (не власним) через
  звичайний `sb.from('profiles').select()` НЕ спрацює — RLS обмежує це власним рядком;
  для такого потрібна окрема `SECURITY DEFINER` SQL-функція.
- Push-сповіщення — Web Push через VAPID-ключі, працює лише для залогінених користувачів
  з профілем (`push_subscriptions.user_id` обов'язковий) — для гостя запитується лише
  системний дозвіл браузера, підписка доприв'язується автоматично після входу.
- Кешування прайсу на пристрої — `localStorage`, звіряється з `price_meta.version`.
- `JOKE_MODE` в index.html — тимчасові жарт-написи в UI. Прибрати виставивши `false`,
  коли набридне/перед "серйозним" релізом.
- RLS `using`/`with check` обмежує РЯДКИ, не КОЛОНКИ — якщо клієнт не повинен мати
  змогу змінити конкретне поле, потрібен додатковий `revoke`/`grant update (<колонки>)`,
  самої RLS-політики мало.
